# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project Overview

This is a **Pine Script v6 TradingView indicator** — a single-file intraday momentum trading system, **forked from SuperLazyTrade with the SuperTrend signal anchor removed**. The sole source file is `SLT.pine`. There is no build system, package manager, or test runner; development means editing the `.pine` file and pasting it into TradingView's Pine Editor to compile and validate.

SLT keeps two signal anchors: **SMA** (default) and **EMA Cross**. The 5-component scoring engine, the 4 risk gates, both P&L tracking systems, win-rate tracking, and the dashboard are carried over from the parent project.

**Light build — minimal input surface.** The settings panel exposes: **Signal Anchor** (EMA Cross / SMA), **Score Stars** (`sigQuality`), **P&L Exit** (`enablePnL` + `pnlTarget`), **Trading Hours** (`tradingHours`, a session window applied uniformly to every asset type), and a **Dashboard & Visuals** group (`showDash`, `extDash`). Every other parameter that was a user input in the parent script is either **auto-tuned** from the asset profile + anchor choice (see [Auto-Tune](#auto-tune-light-build) and the [Profile Parameters Table](#profile-parameters-table)) or **pinned** to its tuned default in a `FIXED BEHAVIOUR` block near the top of the file. The [Index Data Proxy](#key-design-decisions) (the ETF used to source VWAP/volume for a volume-less cash index) is auto-picked by symbol family — **no input**; to hand-pick one, edit the `proxy_ticker` chain in the `INDEX DATA PROXY` block. The **VWAP Fade** module is removed entirely; the **ORB** module is retired but left inert (`orbEnabled = false` constant) so its router/dashboard/plot code still compiles. To change a tuned value, edit the profile `if/else` chain — not the panel.

## Development Workflow

1. Edit `SLT.pine`
2. Copy the full file contents
3. Open TradingView → Pine Editor → paste → Save → Add to Chart
4. Compilation errors appear immediately in the Pine Editor console
5. Test on a 2-minute chart with a liquid instrument (NVDA, TSLA, SPY, QQQ, SOXX, Silver Futures)

## Architecture

The script is organized into sequential sections (read top-to-bottom, order matters in Pine Script):

1. **Constants** — Gate penalty values, dashboard sizing (`DASHBOARD_MAX_ROWS = 36`)
2. **Inputs** — minimal surface (see [Auto-Tune](#auto-tune-light-build)):
   - `grp_anchor`: **Signal Anchor** (EMA Cross / SMA) — the mode selector; drives auto-tune
   - `grp_sig`: **Score Stars** (`sigQuality`) — label selectivity on top of the auto min score
   - `grp_pnl`: **P&L Exit** — `enablePnL` + `pnlTarget`
   - `grp_hours`: **Trading Hours** (`tradingHours`, an `input.session`) — the session window signals may fire in. Applies uniformly to **every** asset type, including 24h futures/crypto — there is no per-profile override.
   - `grp_vis`: **Dashboard & Visuals** — `showDash`, `extDash`
   - *(no proxy input)* — the ETF that sources VWAP/volume for a volume-less cash index is auto-picked by symbol family in the `INDEX DATA PROXY` block. See [Index Data Proxy](#key-design-decisions).
   - `FIXED BEHAVIOUR` block: `showLabels`, `sigTime="Score"`, `gateOn=true`, `rvolMode="Time-of-Day"`, `rvolLookbackDays=10`, `enableSuccessRate`, `maxSignalsToTrack`, `showSignalPnL`, `showCircles=true` — all pinned constants, no inputs. (No `showBg`: the parent's trend-background `bgcolor()` was dropped in the light build, so the toggle would gate nothing; the SMA buffer band's `fill()` is drawn unconditionally in SMA mode.)
   - ORB inert-constant block: `orbEnabled=false` + the 7 ORB tuning constants (module code still present).
3. **Asset profile assignment** — A `switch` on `syminfo.type` first computes `asset_category` (STOCK/FUND/FUTURES/CRYPTO/MARKET); a separate `if/else if` chain keyed on `asset_category` then sets `profile_name`, all scoring threshold variables, the SMA anchor length `sma_len`, **and the three auto-tune fields** `ema_slow_auto` / `sma_buf_auto` / `min_score_auto`. Immediately after the chain, a **TIMEFRAME LENGTH SCALING** block defines `tf_scale` and the deduplicated `len9`/`len14`/`len20`/`len50`/`len10` base-period variables (see [Timeframe Length Scaling](#timeframe-length-scaling)), then an **AUTO-TUNE RESOLUTION** block maps the profile fields (plus the anchor choice) to the effective globals the rest of the script reads: `emaSlowPeriod` (timeframe-scaled from `ema_slow_auto`), `smaBufferATR`, `minScoreBuy`/`minScoreSell` (both = `min_score_auto`), and `maxBarsFromFlip` (`anchorMode=="SMA" ? 0 : len10`). The trading-hours session window is **not** part of this profile resolution — it's the user input `tradingHours`, applied identically regardless of `asset_category` (see [Trading Hours](#key-design-decisions)). See [Profile Parameters Table](#profile-parameters-table).
3b. **Index data proxy resolution** — right after auto-tune resolution, an `INDEX DATA PROXY` block: `chart_has_volume` (a `var` latch that trips only on a sustained ≥50% of the last 100 bars carrying volume — not the first nonzero bar), a `proxy_ticker` auto-picked by `syminfo.ticker` family (+ `proxy_family_known`), one `request.security` pulling the proxy's `[ta.vwap, close, volume, ta.sma(volume,20)]`, and the derived `proxy_eligible` / `proxy_ok` / `use_proxy` flags plus `proxy_vwap_scaled` and `vol_eff`. Only engages when `syminfo.type == "index"`, the chart doesn't carry volume, and the symbol family is recognized. See [Index Data Proxy](#key-design-decisions).
4. **Core indicator calculations** — EMAs (9, `emaSlow`=profile-auto 20 or 30, 20 fixed for scoring, 50), SMA anchor (`smaLenActive = sma_len`, no MANUAL mode), VWAP (`vwap` reassigned once before Component 2 to the proxy-scaled VWAP or a session TWAP when the chart is a volume-less index — see [Index Data Proxy](#key-design-decisions)), ATR(14), RSI(14), ADX(14,14), relative volume (`rvolMode` pinned to Time-of-Day, fed by `vol_eff`; Rolling 20-bar SMA is the automatic thin-history fallback — see [Time-of-Day Relative Volume](#key-design-decisions))
5. **Market regime detection** — Squeeze state (BB(20,2) inside KC(20,1.5×ATR)), squeeze release, stretch factor (EMA distance + trend move since flip), velocity override (ADX>35 rising 3 bars), ATR fuel gauge (session range vs daily ATR-14)
6. **Dual-anchor trend classification** — EMA Cross or SMA mode; `is_bull`/`is_bear`/`trendUp`/`trendDown` unify both anchors behind a single interface, and `anchor_line_price`/`anchor_short` unify the *display* side. `trend_start_price` updated on every `trendUp`/`trendDown`. See [SMA Anchor](#sma-anchor).
7. **Scoring engine** — 5 components summed to `raw_score` (capped at 100). Max theoretical total = 105 across all profiles. See [Scoring Components](#scoring-components).
8. **Risk gates** — 4 gates calculate penalties; applied to `raw_score` → `final_score` only when `gateOn = true`; always shown as warnings regardless. See [Risk Gates](#risk-gates).
9. **Signal generation** — Three sub-stages (regime-router refactor; light build runs **one live module**):
   - **Strategy modules** — each is fully self-gated and exposes `<name>_long` / `<name>_short` / `<name>_quality`:
     - **Trend Pullback** (`tp_*`) — the anchor + 5-component confluence + `passes_quality_filter` logic. `sigTime` is pinned to `"Score"` (fires off `is_bull`/`is_bear` + `entry_is_fresh` + explicit `barstate.isconfirmed`); `"Trend"` mode code is still present but unreachable. Both modes AND in `in_session` and `anchor_ready`. `tp_quality = final_score`.
     - **ORB** (`orb_*`) — Opening Range Breakout, **inert** (`orbEnabled = false`). Code retained. See [ORB Module](#orb-module).
     - ~~**VWAP Fade**~~ — removed entirely from the light build.
   - **Regime router** — `active_strategy` / `strat_long` / `strat_short` / `strat_quality`, last-write-wins: **Trend Pullback (default) → ORB**. With ORB inert, the router always resolves to Trend Pullback. The router only chooses between modules — it never loosens a module's own gating.
   - **Signal dispatch** — `signal_buy = strat_long and not b_fired`, `signal_sell = strat_short and not s_fired`. `b_fired`/`s_fired` enforce strict BUY/SELL alternation **across all modules and any number of regime/trend flips**; they clear only when the opposite signal fires or at trading-hours session open — **not** on a trend-direction change by itself.
   Signals are non-repainting; `barstate.isconfirmed` guards every flip/breakout condition. `stars` (BUY/SELL chart labels) is computed just after the router off `strat_quality`, so it reflects the **active** module. Trading-hours filter via `time(timeframe.period, tradingHours)` (`tradingHours` a user input, default `"0930-1600:23456"`, applied to every asset type) — `in_session`/`session_just_opened` are computed in their own **TRADING HOURS SESSION WINDOW** section placed *before* P&L exit tracking, because the session-open reset must flatten stale position state before `current_pnl` is evaluated on that same bar. Score-mode signals can also be constrained to fire only within `maxBarsFromFlip` bars of the anchor flip (default 0 = disabled); Trend mode is unaffected.
10. **P&L tracking** — Two independent systems: (a) live dashboard P&L using `pnl_entry_price`/`pnl_direction`, reset on every new signal and flattened at trading-hours session open; (b) signal-to-signal `signal_pnl` history shown on labels. PROFIT/LOSS exit triggers fire when `current_pnl` crosses `±pnlTarget` (`target_hit`/`stop_hit`, `in_session`-gated), OR — if the position is still open and unresolved when the session ends — a day-end forced resolution by the sign of P&L at that point (`day_end_win_hit`/`day_end_loss_hit`, detected on `day_end_trigger` — `session_just_closed`, the first off-hours bar, OR a calendar-day-rollover fallback for `tradingHours` windows that never go off-session — using `close[1]`; excluded via `pnl_entry_bar` if the entry opened on the very bar being resolved, which would otherwise force-score a meaningless exact-0% win). Target/stop resolution (`target_reached`/`stop_reached`) is tracked internally regardless of `enablePnL`; `enablePnL` only gates the visible `signal_profit`/`signal_loss`. The dashboard's live P&L (`live_pnl_pct`) freezes at `day_end_frozen_pnl` once day-end-resolved, rather than continuing to drift with the post-resolution close.
11. **Success rate tracking** — Every BUY/SELL trade, **when it closes** (the opposite signal fires, or the RTH session-open carryover), is bucketed into exactly one of three per-direction rolling `array<int>` — `buy_win_s` / `buy_loss_s` / `buy_unr_s` (and the SELL trio) — each holding the `session_seq` **at close time**. **W** = PROFIT (`target_reached`) fired while it was open; **L** = LOSS (`stop_reached`) fired; **U** = neither — reversed on the same trading day before hitting `±pnlTarget` (since day-end forced resolution that's the only way to stay unresolved; anything still open at the close resolves W or L). Every bar the six arrays are front-trimmed to the trailing `WINRATE_LOOKBACK_SESSIONS` (15) trading sessions. `buy_w`/`buy_l`/`buy_u` = the trimmed `array.size(...)`. **Everything the dashboard and verdict show comes from this one window, so the numbers compose:** win rate = `W/(W+L)`, resolved total = `W+L`, fired = `W+L+U`. The **Trade Signal** row (right after Setup Score, before Gates) turns whichever direction fired *last* (`last_signal_type`) into a TRADE/CAUTION/SKIP/WAIT verdict — see [Trade Signal Verdict](#key-design-decisions). **Phase 4:** the W/L outcome is *also* pushed into a per-module store (`mod_results`, a 3-slot `array<ModResults>` indexed by `strat_id()`), keyed by the module that **opened** the entry; U is not tracked per-module. `mod_results` is still a bool array FIFO-capped at `maxSignalsToTrack` (signal count), **not** session-windowed — a divergence left because per-module rows are suppressed in the light build (`multi_module = orbEnabled`); reconcile if a second module goes live. The dashboard shows only the overall BUY/SELL rows in the light build.
12. **Visuals** — Conditional plots, one branch per anchor: EMA9 dynamic line (green/red), or SMA line (green/red) plus its grey ATR buffer band; flip circles at transition bars; BUY/SELL labels anchored to `anchor_line_price` (with a `⚡ORB` tag if ORB were ever active). The locked **ORB high/low** plot (orange, `plot.style_linebr`) is retained but gated on `orbShowLevels = false`, so it never draws. The VWAP fade band plots are deleted.
13. **Dashboard** — `table.new` at `position.bottom_right` with `DASHBOARD_MAX_ROWS = 36`; rendered only on `barstate.islast`. The table is `var`, so every render starts with `table.clear(d, 0, 0, 1, DASHBOARD_MAX_ROWS - 1)`. The gate detail loop is the last section written; it has an explicit `if row >= DASHBOARD_MAX_ROWS: break` guard because it is the only variable-length section. The first data row reports the **active anchor** (`Trend (EMA9)` or `Trend (SMA)`) and its price. The **Signal Anchor** row shows the resolved auto values, e.g. `SMA (90) auto ±0.20A` or `EMA Cross (9/30) auto`. (The **Strategy** row — `active_strategy · <regime>` — was removed; `active_strategy` is always `Trend Pullback` in the light build and the `regime` descriptor had no other consumer, so both it and `sqz_bias` are deleted.) The **ORB** row renders only `if orbEnabled` → never. The **VWAP Fade** row is deleted. The **BUY/SELL Win Rate** rows read `<rate>%  ·  <W>W <L>L <U>↺` — the rate coloured lime/yellow/red by the 60/50 cutoffs (grey when `W+L = 0`), then the raw W/L/U bucket counts over the trailing `WINRATE_LOOKBACK_SESSIONS` (15) trading sessions. Under them, the **per-module win-rate** loop draws one row per module **only in a multi-module build** (`multi_module = orbEnabled`) — suppressed with just Trend Pullback live. The `mod_results` / `record_module` plumbing keeps running, so the rows return intact when a second module goes live; they are styled to match (white label, value `B <r>% <w>/<t>   S <r>% <w>/<t>` colour-coded by the module's combined rate). `dashboard_score` reads `strat_quality`. The **ATR Fuel** row (raw `fuel_used` %/status feeding Gate 3) moved from the always-on core rows into Extended Metrics (`extDash`), right after the **Volatility** row — it duplicated information already reflected in Gates/Setup Score/Trade Signal for everyday decisions, so it's now diagnostic-only, opt-in context (its one unique piece of info, the `🔥 VELOCITY OVERRIDE` state where Gate 3's penalty is waived, isn't visible anywhere else). `DASHBOARD_MAX_ROWS` stays at 36 (headroom; the light build renders well under that).
14. **Alerts** — Four `alertcondition` calls with plaintext messages: `"BUY"`, `"SELL"`, `"PROFIT"`, `"LOSS"`.

## Scoring Components

All 5 components sum to `raw_score`, capped at 100. Component maxes vary by profile but always total 105 before the cap.

| # | Component | Max Points | Varies by Profile? |
|---|-----------|-----------|-------------------|
| 1 | EMA Cascade Alignment | `ema_max` (20–30) | Yes |
| 2 | VWAP Value Anchor | `vwap_max` (15–25) | Yes |
| 3 | Volume Intensity | 25 (fixed) | No |
| 4 | ADX Trend Strength | 15 (fixed) | No |
| 5 | Momentum Confluence | 20 (fixed) | No |

**Component 1 — EMA Cascade (profile-adaptive):**
- Full (`ema_max`): `ema9 > ema20 > ema50` + close on right side of ema9
- Partial (60%): close beyond ema20 but cascade incomplete
- Weak (30%): close beyond ema50 only
- Zero: counter-trend
- Always uses `ema20` (not `emaSlow`) — slow period choice only affects anchor, not scoring
- **Direction is the selected anchor** (`is_bull`/`is_bear`). Component 1 measures how well the EMA cascade confirms the anchor's direction — it is a directional confluence term. (A short-lived experiment keyed it off `ema9` vs `ema20` to make scores numerically comparable across anchors; reverted because it made the term non-directional — see [SMA Anchor](#sma-anchor) → Scoring interaction.)

**Component 2 — VWAP Value (profile-adaptive):**
- BOUNCE/REJECTION (full `vwap_max`): within 0.33× `vwap_h_limit` of VWAP, correct side
- HEALTHY (72%): within `vwap_h_limit`, correct side
- EXTENDED (40%): within `vwap_e_limit`, correct side
- REVERSION RISK (0): beyond `vwap_e_limit`, correct side
- GRACE ZONE (20%): slightly wrong side — bull: within 20% of `vwap_h_limit`; bear: within 10% (intentionally stricter)
- WRONG SIDE (0): too far on wrong side
- The `vwap` series this scores against is the real session VWAP for any symbol with volume. For a **volume-less cash index** it becomes the [proxy](#key-design-decisions)'s VWAP rescaled to index price units (when `use_proxy`), or a session TWAP (running mean of `hlc3` since the session open) if no proxy resolves. Both keep `(close - vwap) / vwap` meaningful, so the tier logic above is unchanged. A volume-less **non-index** symbol (forex) is left as-is — `ta.vwap` returns `na` there and Component 2 scores 0, same as before.

**Component 3 — Volume Intensity:**
- 25pts: RVOL ≥ 2.5× (EXPLOSIVE)
- 20pts: ≥ 2.0× | 15pts: ≥ 1.5× | 10pts: ≥ 1.2× | 5pts: ≥ 1.0× | 0pts: below
- RVOL denominator is `rvolMode`-dependent — point tiers themselves never changed. See [Time-of-Day Relative Volume](#key-design-decisions).
- RVOL is computed from `vol_eff` — the proxy ETF's volume when `use_proxy` (volume-less index), otherwise the chart's own volume. Without a working proxy a volume-less feed still falls back to `rel_vol = 1.0` (fixed 5 pts), exactly as before. See [Index Data Proxy](#key-design-decisions).

**Component 4 — ADX Strength (scales with profile `adx_min`, nested if/elseif — rising (2-bar) qualifies each tier):**
- 15pts: ADX ≥ 1.6× `adx_min` AND rising | 12pts: ADX ≥ 1.6× `adx_min` and NOT rising
- 12pts: ADX in [1.3×, 1.6×) `adx_min` AND rising | 9pts: same range, NOT rising
- 9pts: ADX in [1.0×, 1.3×) `adx_min` (no rising check)
- 6/3/0: moderate (≥0.8×) / weak (≥0.6×) / choppy (below)

**Component 5 — Momentum Confluence (2 sub-components, max 20):**
- 5A RSI (12pts): regime-aware — bull: RSI >60 rising (12) / RSI 45–60 (8) / stalling >60 not rising (3) / else 0. Bear is the exact mirror about 50: RSI <40 **not** rising (12) / RSI 40–55 (8) / stalling <40 rising (3) / else 0. (The bear 12-pt tier was `<45` — near-neutral — until it was tightened to `<40` to actually mirror the bull side.)
- 5B Squeeze Release (8pts): sqz_release + RVOL >1.5 → 8pts; release alone → 3pts
- **MACD sub-component removed** (was 8pts, "MACD line same sign as trend direction"). MACD-line sign ≈ `EMA12 > EMA26`, a near-duplicate of Component 1's EMA cascade, so it carried almost no independent signal. Its 8 points were redistributed proportionally (old 7:5 split) across the two survivors: RSI 7→12, Squeeze 5→8. Component 5 max stays 20; the 105 pre-cap total is unchanged. `ta.macd` call and `macd_aligned`/`macd_pts` are deleted from `SLT.pine`.

**Setup quality rating** (applied to `final_score` after any gate enforcement):

`threshold` = `minScoreBuy` (bull) or `minScoreSell` (bear). In the light build these are **not user inputs** — both resolve to `min_score_auto` (45–55 by profile; see [Auto-Tune](#auto-tune-light-build)) and are always equal on the two sides. `min_score_auto` tops out at 55, so ⭐⭐⭐ EXCELLENT (`threshold + 30` = 85) stays inside the `[0, 100]` clamp for every profile.

- ⭐⭐⭐ EXCELLENT: `final_score ≥ threshold + 30`
- ⭐⭐ STRONG: `≥ threshold + 15`
- ⭐ GOOD: `≥ threshold`
- ⚠️ WEAK: below threshold

## Risk Gates

4 gates total. In **Advisory mode** (`gateOn = false`): shown in dashboard but not applied. In **Enforcement mode** (`gateOn = true`, default): penalties subtract from `final_score`; all use `math.max(..., 0)` floor before the final clamp `[0, 100]`.

| Gate | Trigger | Penalty | Constant |
|------|---------|---------|----------|
| 1 — Squeeze | BB(20,2) inside KC(20,1.5×ATR) | −30 | `SQUEEZE_PENALTY` |
| 2 — Stretch Factor | Unified: MAX(EMA stretch, trend stretch) > `ext_scale` AND no velocity override | −10 or −20 | `STRETCH_MODERATE/EXTREME_PENALTY` |
| 3 — ATR Fuel | Session range > `fuel_max`% of daily ATR-14 AND no velocity override | −25 | `FUEL_PENALTY` |
| 4 — Liquidity | RVOL < `rvol_gate` AND ADX < 90% of `adx_min` | −25 | `LIQUIDITY_PENALTY` |

**Stretch Factor detail:** `stretch_factor = max(ema_stretch, trend_stretch)` where `ema_stretch = |close - ema20| / ATR(14)` and `trend_stretch = |close - trend_start_price| / ATR(14)`. Moderate penalty when `> ext_scale`; extreme when `> ext_scale × 1.5`. **Velocity override** (`is_high_velocity` = `ADX > 35` rising 3 bars) waives the Gate 2 *and* Gate 3 penalties — a genuine high-conviction momentum regime is allowed to run past the standard extension band. The raw stretch tier (`stretch_penalty`/`stretch_status`) is still computed and shown as advisory in the gate message (`gate2_raw`), annotated `🔥 VELOCITY` instead of a `-N`; only the `final_score` subtraction and the dashboard `active_gate_count` are suppressed (`gate2_stretched = gate2_raw and not is_high_velocity`).

## SMA Anchor

The default `anchorMode` option (the other is EMA Cross). Selected when `anchorMode = "SMA"`.

**Length** (`sma_len`) is assigned per asset profile in the profile block — see the `sma_len` column in the [Profile Parameters Table](#profile-parameters-table). In the light build there is no MANUAL mode: `smaLenActive = sma_len` directly.

**Flip semantics — ATR buffer band with latched state.** A raw `ta.crossover(close, sma)` whipsaws badly on a 2-min chart, so the raw cross is not usable as-is. Instead:

```
sma_band = smaBufferATR × ATR(14)          // smaBufferATR = sma_buf_auto (0.20–0.35 by profile)
close > smaAnchor + sma_band  → latch BULL
close < smaAnchor - sma_band  → latch BEAR
inside the band               → hold previous state
```

`sma_state_bull` is a `var bool` initialized `true`, updated only under `barstate.isconfirmed` (so the state cannot flip intrabar and revert — same non-repainting guarantee as the EMA Cross anchor) and guarded by `not na(smaAnchor) and not na(sma_band)` for the warmup bars before the SMA is valid.

**Why latched rather than a true neutral zone:** several downstream consumers are written as `is_bull ? … : …` with no third case (dashboard trend row, anchor line color). If `is_bull` and `is_bear` were both `false` inside the band, those sites would silently render bearish. Latching preserves the strictly-binary `is_bull`/`is_bear` contract that EMA Cross also satisfies. `sma_is_bear` is defined as `not sma_state_bull`, never as an independent test.

Flips derive from the latch by comparing against `sma_prev_bull`, a second `var bool` assigned from `sma_state_bull` *before* the update block each bar. This is deliberately not `sma_state_bull[1]`: that reads `na` on bar 0, making the flip booleans `na` rather than `false`, and `nz()` has no bool overload to default it with (`CE10123` — `nz` expects a numeric `source`). Because flips come from the latch, `trend_start_price` and `bars_since_flip` stay correct with no extra work, and `maxBarsFromFlip` applies to SMA mode in Score mode exactly as it does to EMA Cross.

(`sma_buf_auto` is always > 0 in the light build; setting a profile value to 0 would degrade to a raw price/SMA cross with substantially more flips.)

**Scoring interaction — be aware of it (not corrected):** Component 1 (EMA Cascade) conceptually overlaps the SMA anchor — both measure price against a slow average. In SMA mode `is_bull` (price above a 70–120-bar SMA) holds through pullbacks that would already have flipped an EMA-cross anchor, so Component 1 keeps awarding PARTIAL/WEAK points during choppy continuation where EMA-cross mode would score the bar 0 or as the opposite side. Net: **SMA-mode `raw_score` skews slightly higher on trend continuation** — factor this in when comparing win rates across the two anchors; the score distributions are not strictly comparable.

An experiment (commit `c0d85a1`, reverted) keyed Component 1's bull/bear branch off `ema9` vs `ema20` instead of `is_bull`/`is_bear` to normalize this. It backfired: `t_pts` is added to `raw_score` unconditionally with no re-check against the signal's direction, so decoupling made Component 1 a non-directional term — it suppressed with-trend pullback BUYs (PARTIAL→COUNTER-TREND) and added full-cascade points to counter-trend SELLs when the EMAs were bullish. If normalization is revisited, do it by shifting a few points from `ema_max` to `vwap_max` in SMA mode (VWAP/price is genuinely independent of a price/SMA anchor), never by changing the direction selector.

## ORB Module

> **Light build status: INERT.** `orbEnabled` is a constant `false` (not an input). The module code below, its dashboard row (`if orbEnabled`), and its plots (`orbShowLevels = false`) all remain in the file and compile, but nothing activates. The 7 former ORB inputs are kept as constants so those references resolve. Re-enabling means turning the constant back into an input. The description below documents behaviour *if re-enabled*.

Second strategy module (Phase 2 of the regime-router refactor). Lives in the STRATEGY MODULES section between Trend Pullback and the router.

**State (`var`, reset on `session_just_opened`):** `orb_open_time` (epoch ms of the RTH open bar — the session anchor), `orb_high` / `orb_low`, `orb_locked`, `orb_done` (one breakout per session).

**Range build → latch.** On the session-open bar, seed `orb_high/orb_low` = that bar's `high`/`low`. On each subsequent **confirmed** in-session bar while `orb_mins < orbMinutes` (where `orb_mins = (time - orb_open_time) / 60000`), extend the high/low. The first confirmed bar at/after `orbMinutes` sets `orb_locked := true` and stops extending. Confirmed-bar-only updates keep it non-repainting, same as the anchors.

**Anchored to `session_just_opened`,** which now fires for every asset type (`tradingHours` applies universally — see "Trading Hours" in [Key Design Decisions](#key-design-decisions)), so there's no more "filter off" case where `orb_open_time` would stay permanently `na`. (When ORB was written, `session_just_opened` was gated on a per-profile `useSessionFilter` that could be permanently off for FUTURES/CRYPTO; that gate no longer exists.)

**Breakout trigger** (`orb_long` / `orb_short`), all required, all on a confirmed bar:
- `orb_locked` and not `orb_done` (one per session)
- `orb_mins <= orbEntryCutoffMin` (0 = no cutoff)
- `close > orb_high + orbBufferATR×ATR(14)` (long) / `close < orb_low - …` (short)
- `rel_vol >= orbMinRvol` (0 disables)
- VWAP alignment if `orbRequireVwapSide` (long: `close > vwap`)
- `orb_quality >= orbMinQuality`

`orb_done := true` on the firing bar (evaluated after the trigger booleans, so the signal still passes through that bar).

**`orb_quality` (0–100)** — additive, `math.min(…, 100)`: range geometry (30 for range 0.75–2.0 ATR / 18 for 0.5–3.0 / else 8) + breakout `rel_vol` (30/22/14/6/0 at ≥2.0/1.5/1.2/1.0/else) + VWAP-side alignment (12) + anchor-direction agreement (8) + ATR fuel left (20/12/5 at `fuel_used` <50/<75/<`fuel_max`). Feeds `strat_quality` (and thus `stars` / dashboard Setup Score) when ORB is the active strategy.

**Router interaction:** `if orb_long or orb_short` → `active_strategy := "ORB"` and `strat_*` take the `orb_*` values, overriding Trend Pullback for that bar. Everything downstream (dispatch alternation, P&L, win-rate, labels `⚡ORB`, alerts) is module-agnostic and needs no ORB-specific code.

**Not modelled yet:** failed-breakout / reversal entries (only the first break each session is taken), and a separate ORB stop/target (P&L exits are still the global Fixed-% system).

## Timeframe Length Scaling

Every bar-count lookback in the script (EMA9/20/50, the profile SMA length, ATR/RSI/ADX(14), the squeeze BB/KC(20) lengths, the 20-bar RVOL fallback, `maxBarsFromFlip`) was tuned to cover a specific amount of real time on a **2-minute chart** (the tested interval — see [Development Workflow](#development-workflow)). A fixed bar count covers a different amount of wall-clock time on any other interval — e.g. the STOCK profile's `sma_len=70` covers ~2.3h on a 2-min chart but ~5.8h on a 5-min chart if left unscaled.

`tf_scale = BASE_TF_SECONDS / timeframe.in_seconds()` (`BASE_TF_SECONDS = 120`, the 2-min reference) rescales every such length so each one keeps covering the same wall-clock window regardless of chart interval. On a 2-min chart `tf_scale = 1.0` exactly, so behavior is byte-for-byte unchanged from before this feature — 2-min remains the reference calibration and the only interval this script's thresholds are actually validated against. Non-intrabar chart types (Range/Tick/Renko) report `timeframe.in_seconds() == 0`; `tf_scale` falls back to `1.0` (unscaled) in that case, since there's no wall-clock equivalent to scale against.

**Implementation note — no shared helper function.** `ta.ema`/`ta.sma`/`ta.atr`/`ta.rsi`/`ta.dmi`/`ta.bb` all require a `simple int` length argument. A user-defined Pine function's return value is always widened to `series` by the compiler, even one that does nothing but arithmetic on already-`simple` inputs — Pine can't verify a function stays `simple` across every possible call site, so a `scale_len(base_len) => ...` helper was tried first and failed to compile (`CE10123: An argument of "series int" type was used but a "simple int" is expected`). The fix is to compute each scaled length inline, as a plain expression assigned to a `simple int` variable, and reuse that variable by reference (a variable reference doesn't widen the qualifier the way a function call does). The four base periods (9/14/20/50) are deduplicated into `len9`/`len14`/`len20`/`len50` since several call sites share a base period; `len10` is `maxBarsFromFlip`'s base. Each is `int(math.max(1.0, math.round(base * tf_scale)))`.

**Scaled:** `ema9Period` (= `len9` — kept as a named variable rather than inlined so the dashboard's `EMA Cross (n/…)` label reflects the real period instead of a hardcoded "9"), `emaSlowPeriod` (scaled from `ema_slow_auto`), `ema50` (`len50`), `ema20` (`len20`, Component 1 scoring), `smaLenActive` (scaled from `sma_len`), the `atr`/`rsiVal`/`adx` 14-periods (`len14`), the squeeze `ta.bb`/`ta.atr` 20-periods (`len20`), the `vol_ma20` RVOL fallback 20-period (`len20`), and `maxBarsFromFlip` (`len10` in EMA Cross mode; still `0` — unlimited — in SMA mode).

**Not scaled (deliberately):** the profile threshold/percentage values (`vwap_h_limit`, `vwap_e_limit`, `adx_min`, `ext_scale`, `fuel_max`, the RVOL point tiers) — these were tuned against 2-min bar noise/volatility characteristics and have no comparable scaling law, so switching interval still means re-validating those by eye; they are not addressed by this feature. Also left alone: `rvolLookbackDays` / `maxSignalsToTrack` (session/signal counts, not bar-lookback windows) and the 2–3 bar `ta.rising()` momentum checks (`adx_rising_2`, `adx_rising_3`, `rsi_rising`) — at that length, scaling either collapses to a meaningless 1-bar check or adds complexity for no real calibration benefit. The daily ATR (`atr_14`, `request.security(..., "D", ...)`) is unaffected by chart interval by construction.

## Key Design Decisions

**Profile-adaptive scoring:** `ema_max` and `vwap_max` vary by asset type (e.g., FUTURES gets `ema_max=30`, `vwap_max=15`), so the raw 100-point maximum is assembled differently per profile. All profiles sum to 105 before the cap. When modifying component weights, check all five profiles.

**Strategy router (light build):** Signal generation is still structured as *strategy modules → router → dispatch*, but only **Trend Pullback** (`tp_*`, the anchor + confluence logic) is live. **ORB** (`orb_*`) code is present but inert (`orbEnabled = false`); **VWAP Fade** is deleted. The router (`active_strategy`/`strat_long`/`strat_short`/`strat_quality`) resolves last-write-wins Trend Pullback → ORB, so with ORB off it always yields Trend Pullback. (The descriptive `regime` classification sub-stage and its dashboard Strategy row were removed — nothing consumed `regime` after VWAP Fade.) Every downstream consumer (P&L, win-rate, labels, alerts, dashboard) still fires off the dispatched `signal_buy`/`signal_sell` / the `strat_*` surface, so the module machinery is intact. Per-module win-rate (`mod_results`) still exists; only slot 0 (Trend Pull) ever fills. **When re-adding a module:** expose `<name>_long`/`<name>_short`/`<name>_quality`, keep it fully self-gated, register it in the router (opposite-stance modules go *above* Trend Pullback and must carry a regime gate), let dispatch apply alternation, and wire a `strat_id()` slot + dashboard row. The `sigTime="Trend"` path in Trend Pullback is also dead code (pinned to `"Score"`).

**Dual-anchor unification:** After anchor selection, all downstream logic uses `is_bull`, `is_bear`, `trendUp`, `trendDown` — never `ema_*` or `sma_*` directly. The scoring engine, all 4 risk gates, signal generation, and both P&L systems are anchor-agnostic through this interface. `maxBarsFromFlip` is the deliberate exception: it resolves to `anchorMode == "SMA" ? 0 : 10`. The EMA slow period (`emaSlowPeriod = ema_slow_auto`, 20 or 30 by profile) affects cross detection but NOT Component 1 scoring, which always uses `ema20`. Component 1's bull/bear branch is selected by `is_bull`/`is_bear` like the other directional components (a `c1_bull`/`c1_bear` decoupling was tried and reverted — see [SMA Anchor](#sma-anchor)). Only the Score-mode signal branch is live (`sigTime` pinned to `"Score"`); the Trend-mode branch is retained but unreachable.

The anchor selectors are **binary ternary chains** (`anchorMode == "SMA" ? … : …`), every one ending in the EMA Cross branch — so any `anchorMode` value other than `"SMA"` resolves to EMA Cross behavior rather than erroring. A new anchor would have to be added to all four selectors plus `anchor_line_price`, `anchor_short`, and `anchor_ready` explicitly. Only the *drawing* sites (`plot`, `plotshape`, `fill`, dashboard `anchor_display`) use explicit `anchorMode == "..."` equality, so an unhandled mode draws no anchor line at all — which is the symptom to look for.

**`anchor_ready` — anchor warm-up guard:** `ta.sma` returns `na` until `smaLenActive` bars exist (70–120 by profile), and `sma_state_bull` is initialized `true` with its update block skipped while `smaAnchor` is `na`. The SMA anchor therefore reports `is_bull = true` for its whole warm-up window regardless of price direction. `anchor_ready` (`not na(smaAnchor)` in SMA mode, `true` otherwise) is AND'd into both the Trend-mode and Score-mode signal branches to block that. It matters most in the default configuration — Score timing with `maxBarsFromFlip = 0` — where nothing else would stop a warm-up BUY from firing on score alone in a downtrend, seeding the win-rate array and drawing its label at a `na` price. Both EMAs produce usable values from the first bars, so EMA Cross mode passes `anchor_ready` unconditionally.

**Non-repainting:** *Signals* are non-repainting — `barstate.isconfirmed` guards every flip condition and all signal assignments. The daily ATR (`atr_14`) uses `request.security(..., lookahead_off)`, which reads the *developing* daily bar, so `fuel_used` drifts upward through the session. This is **not** display-only — it feeds Gate 3 (ATR Fuel) and therefore `final_score` and signal generation. It is still non-repainting: `lookahead_off` guarantees the value is computed from data available at that bar, so a historical bar recomputes to the same number it had live.

**Gate vs advisory mode:** Setting `gateOn = true` (default/recommended) subtracts gate penalties from `final_score`, directly suppressing low-ADX/range-bound chop entries (Gates 1 and 4 in particular). Setting `gateOn = false` shows gate warnings in the dashboard but does NOT subtract from `final_score`. Component 5B (Squeeze Release) is always active regardless of gate mode, to keep scoring consistent.

**Signal blocking (strict alternation):** `b_fired`/`s_fired` block a same-direction signal from firing again — in both "Trend" and "Score" signal-timing modes — until the opposite signal actually fires, no matter how many trend flips happen in between. E.g. BUY fires, trend flips bear but SELL's score/quality filter never clears, trend flips bull again → BUY stays blocked. The flags do **not** reset on a trend direction change by itself (`is_bull` vs `is_bull[1]`); they only clear when `signal_buy`/`signal_sell` actually fires (`b_fired := true, s_fired := false` and vice versa) or at trading-hours session open (`session_just_opened`, driven by `tradingHours` — now applies to every asset type, so every profile gets a daily reset, including 24h futures/crypto). Live P&L tracking (`pnl_entry_price`, dashboard P&L, signal-to-signal P&L history) does not consult these flags and keeps accumulating across the held direction regardless.

**Trading Hours — applies to every asset type:** `tradingHours` (`grp_hours`, an `input.session`, default `"0930-1600:23456"` = 09:30–16:00 Mon–Fri) drives `in_session`/`session_just_opened` via `time(timeframe.period, tradingHours)`, uniformly for every profile — MARKET/FUND/STOCK/FUTURES/CRYPTO alike. There is no more per-profile on/off: the earlier design (`rth_auto`, `false` for FUTURES/CRYPTO so a 24h contract wouldn't get blacked out by a hardcoded RTH window) was replaced because it caused the opposite problem in practice — 24h futures signals fired around the clock with no hours restriction at all, which is not what a day-trader using a futures profile actually wants. `tradingHours` is now the single, always-enforced control; there is no toggle to disable it and run a symbol with no hours restriction. If that's ever needed, widen the session (e.g. `"0000-2359:1234567"`) rather than reintroducing a profile-level bypass — `input.session`'s own picker exposes both the time range and the day-of-week mask, so the returned string already matches the exact format `time()` expects (`"HHMM-HHMM:DDDDD"`), which is why swapping the hardcoded literal for the input variable required no other code changes at any of its three read sites (`in_session`, `prev_in_session`, and — indirectly, via `session_just_opened` — the ORB module's range anchor).

**`tradingHours` is designed for a single continuous range only.** `input.session` also accepts a comma-separated multi-range string (e.g. a lunch-break split like `"0930-1130,1300-1600:23456"`) — `in_session` correctly reports "inside any sub-range" for such a string, but `session_just_opened`/`session_just_closed` fire at *every* sub-range boundary, not just the real start/end of the trading day. That would trigger the daily flatten/reset and the day-end forced P&L resolution (below) at each internal gap, prematurely force-scoring an open position at, say, the lunch break instead of at the actual close. Not auto-corrected: distinguishing "the last sub-range of today" from an internal gap isn't derivable from `in_session`/`prev_in_session` alone without parsing `tradingHours` itself. Documented in the input's own tooltip and a code comment at its definition rather than fixed — keep `tradingHours` to one range.

**Entry freshness constraint:** `maxBarsFromFlip` is auto-set from the anchor: `anchorMode == "SMA" ? 0 : 10` (SMA latches on the flip bar so it needs no cap; EMA9/slow crosses lag the turn so entries are capped at 10 bars past the flip). It constrains Score-mode entries via `entry_is_fresh = maxBarsFromFlip <= 0 or bars_since_flip <= maxBarsFromFlip`. `bars_since_flip` (`var int`) resets to 0 on the flip bar and increments after, in sync with the `trend_start_price` reset. This is independent of (and complements) the Stretch gate. Calibrate a profile-specific value by editing the resolution-block ternary; observe via the Extended Metrics "Bars From Flip" row.

**Two P&L tracking systems (independent):**
- *Live dashboard P&L* — tracks position from `pnl_entry_price`, reset on every new `signal_buy`/`signal_sell`. Since strict alternation (see Signal Blocking above) means there's only ever one signal per held direction, entry always corresponds to the signal that opened the current position — a separate "First Signal" reset-on-direction-change mode is no longer meaningful and was removed.
- *Signal P&L History* — shown on BUY/SELL labels; calculates `%` move from `last_signal_price` to current close using the previous signal's direction. Completely separate state from dashboard P&L.

**P&L exits fire on target/stop hit, or are forced at day's end:** `normal_target_reached`/`normal_stop_reached` fire when `current_pnl` (computed from `pnl_entry_price`) crosses `±pnlTarget` (`target_hit`/`stop_hit`), once per entry, on a confirmed bar, while `in_session`. `target_reached = normal_target_reached or day_end_win_hit` (`stop_reached` mirrors it) also fires — so all downstream consumers (win-rate, `pnl_exit_fired`, labels, alerts) are automatically covered by the same two booleans — if the position is still open and unresolved when a `day_end_trigger` fires. `day_end_trigger = session_just_closed or day_end_fallback`: `session_just_closed = not in_session and prev_in_session` (the exact same `in_session`/`prev_in_session` primitives `session_just_opened` already uses, just inverted — fires on the FIRST off-hours bar, one bar after the actual close) is the normal path; `day_end_fallback = is_new_session and in_session and prev_in_session and not target_hit and not stop_hit` is a fallback for a `tradingHours` window that covers every bar (e.g. widened to `"0000-2359:1234567"` for a 24h symbol), where `in_session` never goes false so `session_just_closed` can never fire — it instead triggers off the calendar-day rollover (`is_new_session`, the same detector the daily ATR fuel gauge / Time-of-Day RVOL already use), guarded against co-firing with a genuine same-bar target/stop hit. At the trigger bar, `day_end_pnl` is computed from `close[1]` (the real last-bar-of-the-period price, not whatever the current bar has drifted to), and `day_end_win_hit = day_end_close and day_end_pnl >= 0` / `day_end_loss_hit = day_end_close and day_end_pnl < 0`. `day_end_close` additionally requires `pnl_direction != "NONE"`, `not pnl_exit_fired`, and `pnl_entry_bar < bar_index - 1` — the last guard excludes an entry that opened on the very bar the trigger is resolving, since `close[1]` there trivially equals the entry price and would otherwise force-score a meaningless exact-0% "win"; such an entry is left unresolved instead, same as any other same-day reversal that never hits target or stop. This is what stops a position from drifting through off-hours bars (see "Trading Hours forced day-end resolution" in [Key Design Decisions](#key-design-decisions)) — every entry that had real market exposure is now guaranteed to resolve within the trading day it opened, one way or the other. `signal_profit`/`signal_loss` are `target_reached`/`stop_reached` AND `enablePnL`, and drive only the labels and alerts. `normal_target_reached`/`normal_stop_reached` (require `in_session`) and `day_end_win_hit`/`day_end_loss_hit` are mutually exclusive by construction — the off-hours path requires `not in_session`, and the fallback path explicitly excludes `target_hit`/`stop_hit` — so checking `day_end_win_hit`/`day_end_loss_hit` directly (not `in_session`, which the fallback can leave `true`) tells the label-drawing code which path resolved a given bar. The exit LABEL text and position differ per path even though they share one alert: a true `target_hit`/`stop_hit` shows the fixed target text (`PROFIT +1.0%` / `LOSS -1.0%`) anchored at the current bar; a day-end forced resolution shows the actual `day_end_pnl` instead (`PROFIT +0.7%` / `LOSS -0.3%` — both use the same word as the fixed-target case either way, only the % source differs) anchored at `bar_index - 1`/`close[1]`, since the code itself runs one bar after the period actually ended. This anchor math and the `pnl_exit_type` style mapping are factored into shared helpers, `day_end_label_anchor()`/`exit_label_style()`, used by both the PROFIT and LOSS label blocks.

**Why `session_just_closed` instead of detecting the last in-session bar directly:** an earlier attempt tried `is_last_session_bar = in_session and na(time_close(timeframe.period, tradingHours))`, reasoning that a bar's own close timestamp is already known the moment it opens (not future data), so checking whether *that* falls outside the session should be safe without look-ahead. In practice this never fired — `time_close(timeframe, session)` did not behave the way `time(timeframe, session)` does for detecting a boundary crossing. Detecting the session's end one bar late via `session_just_closed`, reusing the exact mechanism `session_just_opened` already relies on and is already proven correct, is far more reliable. The cost is that the resolution (and its alert) technically fires one bar after the session closed; the label/alert's *displayed* P&L and position are still correct because they use `close[1]`/`bar_index - 1`, not the current (off-hours) bar's price.

**`enablePnL` is display-only — it must not gate resolution:** win-rate scoring reads `target_reached`, *not* `signal_profit`. If it read `signal_profit`, turning off "Enable P&L Exit Signals" (presented purely as a label/alert toggle) would make every tracked entry resolve as a loss and pin both win rates at 0% with no warning. Keep any future outcome/statistics logic on `target_reached`/`stop_reached`.

**Position state is flattened at trading-hours session open:** when `session_just_opened`, `pnl_entry_price`/`pnl_direction`/`pnl_exit_fired`/`pnl_exit_type` are all reset, matching the win-rate tracker which already closes any carried-over entry at that boundary. Without this, yesterday's entry price survives into the new session and an opening gap can immediately fire a PROFIT or LOSS label *and alert* against a position the tracker already considers closed. This is why the TRADING HOURS SESSION WINDOW section sits *above* P&L exit tracking in the file — the reset has to land before `current_pnl` is computed on the session-open bar. This now applies uniformly to every asset type, including 24h futures/crypto (see "Trading Hours — applies to every asset type" in [Key Design Decisions](#key-design-decisions)) — there is no more per-profile exemption.

**Win-rate tracking — one session window, three buckets (W / L / U):** every BUY/SELL trade, **when it closes** (the next opposite-direction signal fires, or the `session_just_opened` carryover), lands in exactly one of three per-direction `var array<int>`, each holding the `session_seq` **at close time**:
- `buy_win_s` / `sell_win_s` (**W**) — PROFIT (`target_reached`) fired at some point while the trade was open.
- `buy_loss_s` / `sell_loss_s` (**L**) — LOSS (`stop_reached`) fired while it was open.
- `buy_unr_s` / `sell_unr_s` (**U**) — neither fired: the trade was reversed on the **same trading day** before hitting `±pnlTarget`. Since day-end forced resolution this is the *only* way to stay unresolved — anything still open at the trading-hours close is forced to W or L there. U is its own bucket now, **not** silently dropped.

`buy_won_this_entry` / `buy_lost_this_entry` (`var bool`, mirror for SELL) accumulate `target_reached`/`stop_reached` during the open trade (at most one fires per trade — `pnl_exit_fired` latches after the first). At close, an `if won / else if lost / else` picks the bucket and `array.push(<bucket>, session_seq)`. `buy_entry_open`/`sell_entry_open` guard against scoring before a trade has opened; all three flags are cleared both at the opposite-signal close **and** the carryover close (clearing at only the latter was a historical double-count bug).

**Every bar**, the six arrays are front-trimmed to the trailing `WINRATE_LOOKBACK_SESSIONS` (15) trading sessions — an unconditional front-trim (no scan) is correct because `session_seq` is pushed in non-decreasing order. `buy_w`/`buy_l`/`buy_u` (and SELL) = the trimmed `array.size(...)`, recomputed every bar (not `var`). `session_seq` is the same `var int` calendar-day-rollover counter (`is_new_session`) the ATR Fuel gauge and Time-of-Day RVOL use; **trading sessions, not calendar days**, so weekends/holidays don't shrink the window (mirrors the `rvolLookbackDays` convention). Like `rvolLookbackDays`/`maxSignalsToTrack`, `WINRATE_LOOKBACK_SESSIONS` is a session count, deliberately **not** rescaled by `tf_scale`.

**Everything on the dashboard and in the verdict comes from this one window, so the numbers compose:** win rate `success_rate_buy` = `W / (W + L)`; resolved total `totalTrades_buy` = `W + L`; the Trade Signal verdict's "fired" = `W + L + U`. Computed by `winrate_stats(wins, losses, enabled) => [w, t, rate]` (a trivial read-only helper — `calc_win_rate` on bool arrays is retained only for the per-module rows). The currently-open trade is never counted until it closes; a trade that closes on the current bar shows up in the counts one bar later (the trim + `buy_w` read happen in *SUCCESS RATE TRACKING*, the pushes in *UPDATE SUCCESS RATE TRACKING* just after — a pre-existing one-bar lag). *(The earlier design capped `buy_results`/`sell_results` at `maxSignalsToTrack` by signal count while `(N fired)` was session-windowed separately — the two windows never composed, so `fired ≥ resolved` wasn't guaranteed. Unifying on one session window removed that.)*

**Fired-count / window (folded into Win-rate tracking):** `fired` is no longer a separate quantity — it's `W + L + U` over the single `WINRATE_LOOKBACK_SESSIONS` window described above. There is no more `buy_signals_fired`/`buy_fire_sessions` state, no `maxSignalsToTrack` cap on the overall arrays, and no `(N fired)` on the dashboard (the row shows `<rate>%  ·  <W>W <L>L <U>↺` instead). `session_seq` (the `is_new_session` calendar-day-rollover counter) and the "trading sessions not calendar days" rationale carry over unchanged.

**Trade Signal verdict:** a `Trade Signal` dashboard row, drawn immediately after Setup Score and before Gates — deliberately *not* grouped with the BUY/SELL Win Rate rows it reads from, so it reads as a top-level call alongside Setup Score rather than a footnote under Success Rate Tracking — turns the resolved win-rate stats for whichever direction fired *last* (`last_signal_type`) into a plain TRADE/CAUTION/SKIP/WAIT call, rather than requiring the user to read the raw win rate and mentally adjust for sample size. It deliberately tracks only one direction at a time (the last-fired one) — not a combined BUY+SELL verdict and not two separate always-on rows — since a live BUY and a live SELL are never both "the current call" at once given strict alternation. Computed by `trade_verdict(wins, total, fired, target)`, called right after `last_signal_type` is updated in *UPDATE SIGNAL P&L TRACKING* (not up in *SUCCESS RATE TRACKING* where `totalWins_*`/`totalTrades_*` are computed) so a signal firing on the current bar is reflected immediately rather than lagging one bar behind. Three gates, in order:
1. **Sample size** — fewer than `VERDICT_MIN_SAMPLE` (10, `const int`) resolved entries for that direction → `WAIT (n/10)`, regardless of how good the raw rate looks. Same rationale as the Wilson step below: a 3/4 win rate is not evidence of anything yet.
2. **Resolution rate** — `resolved / fired` = `(W + L) / (W + L + U)`, a clean `[0, 1]` ratio now that both come from the same window (the old design divided a signal-count-capped `resolved` by a session-windowed `fired`, which could exceed 1.0). Below `VERDICT_MIN_RESOLUTION` (0.40, `const float`) → `SKIP (CHOPPY)`, overriding whatever the win rate says: below this floor most signals in that direction are getting reversed (`U`) before ever hitting target or stop, so the resolved sample is a thin, self-selected slice — not representative of trading every signal.
3. **Wilson-adjusted win rate** — otherwise, `wilson_lower_bound(wins, total)` (95% confidence, `WILSON_Z = 1.96`, `const float`) shrinks the raw win rate toward 50% as `total` gets small — the same statistical correction that turned the crude oil chart's raw 84.6%/87.5% into ~58%/53% in a spot-check — and that adjusted rate is judged against the *same* 60/50 tier cutoffs the win-rate row colors already use: `≥60%` → `TRADE`, `≥50%` → `CAUTION`, below → `SKIP`. The verdict string also appends the implied per-trade expectancy, `target × (2 × wlb − 1)` where `target = pnlTarget` (valid because entries exit at a symmetric fixed `±pnlTarget`, so a single win-rate number pins down expectancy with no separate reward:risk term needed) — e.g. `TRADE (+0.16%)`.

`wilson_lower_bound` and `trade_verdict` are both read-only helpers (local-variable reassignment only, same pattern as `calc_win_rate`) defined together with it in the *SUCCESS RATE TRACKING* section. The row reads `—` (grey) until `has_previous_signal` is true. All three thresholds (`VERDICT_MIN_SAMPLE`, `VERDICT_MIN_RESOLUTION`, `WILSON_Z`) are pinned constants, not inputs, consistent with the light build's minimal input surface — see [Auto-Tune](#auto-tune-light-build).

**Trading Hours forced day-end resolution:** before this, a position still open with neither target nor stop hit would simply drift through off-hours bars — where `current_pnl` kept being computed and could cross `±pnlTarget` on a bar outside trading hours, firing a PROFIT/LOSS label + alert with no trading-hours check at all (the bug this fixes) — and would only get closed out (and, per the rule above, excluded as unresolved) once the NEXT session's `session_just_opened` carryover-close ran. Now `day_end_trigger = session_just_closed or day_end_fallback` (see [Trading Hours](#key-design-decisions) and the P&L exits paragraph above) detects the resolution point: `session_just_closed = not in_session and prev_in_session`, the exact mirror of `session_just_opened`, for the normal off-hours case; `day_end_fallback`, keyed off the calendar-day rollover `is_new_session`, for a `tradingHours` window that never actually goes off-session (e.g. widened to cover 24h) where `session_just_closed` would otherwise never fire — a gap a code review caught: without the fallback, the "every entry resolves same day" guarantee silently didn't hold for a widened-hours symbol, letting a position carry indefinitely. At the trigger bar, if the position hasn't resolved yet (`pnl_direction != "NONE"`, `not pnl_exit_fired`, and `pnl_entry_bar < bar_index - 1` — the last guard excludes an entry opened on the very bar being resolved, which would otherwise force-score a meaningless exact-0% win since `close[1]` there trivially equals the entry price), it's forced to resolve by the sign of `day_end_pnl`, computed from `close[1]` (the actual last-bar-of-the-period price, not the current bar's, which may have already drifted further): `day_end_win_hit` / `day_end_loss_hit`. These feed directly into `target_reached`/`stop_reached` (see the P&L exits paragraph above) rather than being a separate mechanism, so every downstream consumer — win-rate scoring, `pnl_exit_fired` latching, the PROFIT/LOSS labels and alerts — picks this up automatically with no new plumbing. The normal path requires `in_session`; the fallback path explicitly excludes a same-bar `target_hit`/`stop_hit`; so the two can never both resolve the same bar. The label/alert is anchored back to `bar_index - 1`/`close[1]` (the real last-bar-of-the-period) at the draw site, since the code itself executes one bar late; see "why `session_just_closed` instead of the last in-session bar directly" in the P&L exits paragraph for why detecting the close a bar late — rather than trying to catch the exact last in-session bar itself — is the reliable choice here. `pnl_entry_price`/`pnl_direction` themselves are *not* flattened immediately at day-end (only `pnl_exit_fired`/`pnl_exit_type` update, same as any target/stop hit) — the existing `session_just_opened` flatten at the next session's open still does that, consistent with how a same-day target/stop hit already keeps "Live P&L continues" on the dashboard until the position is actually closed. The dashboard display is the one exception: `day_end_frozen_pnl` (set to `day_end_pnl` when `day_end_close` fires, read first in the `live_pnl_pct` calc, cleared on the next new entry or session-open flatten) freezes the *displayed* live P&L at the day-end value instead of letting it keep drifting with the post-resolution close — a normal in-session target/stop hit is unaffected and keeps updating live as before.

**Per-module win-rate (Phase 4):** every W or L close (the two in *UPDATE SUCCESS RATE TRACKING* and the carryover close) also calls `record_module(mod_results, strat_id(<dir>_entry_strategy), is_buy, won, cap)` — **W/L only; the U bucket is not mirrored per-module**. `mod_results` is a `var array<ModResults>` (UDT wrapping `array<bool> buys` / `array<bool> sells`, because Pine arrays can't nest — same trick as `TodSession`), populated once with 3 slots, still **FIFO-capped at `maxSignalsToTrack` by signal count** — it was *not* migrated to the session window, since its rows are suppressed in the light build. Reconcile the windowing (and decide whether to add a U column) when a second module goes live. `strat_id()` still maps `0` Trend Pullback / `1` ORB / `2` VWAP Fade (anything unknown → 0) — the ORB and Fade mappings are vestigial in the light build. `<dir>_entry_strategy` (`var string`) is stamped from `active_strategy` at the moment the entry opens. `record_module` mutates the UDT's inner array in place (reference type reachable through the `store` parameter). The per-module dashboard rows are gated on `multi_module` (`= orbEnabled`) — in the single-module light build they are suppressed entirely because they would duplicate the BUY/SELL Win Rate rows. `record_module` still runs, so slot 0 accumulates and the rows would render correctly the moment a second module is live; when shown they match the BUY/SELL Win Rate style (white label, value colour-coded by the module's combined rate via `calc_win_rate` on `mr.buys` + `mr.sells`).

**Dashboard row budget:** `DASHBOARD_MAX_ROWS = 36` (rows 0–35). The `28→30→32→36` bumps came from the router phases (optional ORB row, Fade row, up to 3 per-module rows). The light build deleted the Fade row, made the ORB row unreachable, and suppresses the per-module rows in single-module mode, so the live worst case is well under 36. The gate detail loop is the last section; it has an explicit `if row >= DASHBOARD_MAX_ROWS: break` guard because it is the only variable-length section (all other rows are fixed-count by design). Success Rate Tracking occupies 3 fixed rows (separator + BUY Win Rate + SELL Win Rate), regardless of Extended Metrics; the `Trade Signal` row is a separate fixed row inserted right after Setup Score (both gated on `enableSuccessRate`, since both read the W/L/U buckets). The constant stays at 36 as slack for re-adding a module (which brings its per-module rows back).

**VWAP grace zone asymmetry:** Bull grace zone tolerance = `vwap_h_limit × 0.2`; bear grace zone = `vwap_h_limit × 0.1`. Bears are held to half the tolerance — intentional, reflecting that short-side entries near VWAP carry more reversion risk.

**Time-of-Day Relative Volume:** `rel_vol` (used by Component 3, Gate 4 liquidity, and Component 5B squeeze-release) is `rvolMode`-dependent. Default `"Time-of-Day"` compares current bar volume to the average volume of the *same bar-slot* (bars since session open) across the prior `rvolLookbackDays` completed sessions — this removes the U-shaped intraday volume bias that a trailing SMA has (overstates RVOL near the open, understates it at lunch). History is kept in `array<TodSession>`, where `TodSession` is a UDT wrapping `array<float>` — Pine cannot nest arrays directly (`array<array<float>>` is not supported), so a UDT wrapper is the standard workaround. Session boundaries reuse the existing `is_new_session` (calendar-day change) detector, so the same extended-hours caveat applies as the ATR Fuel gauge. Falls back to the `ta.sma(volume, 20)` method (`"Rolling 20-bar"`) when fewer than 3 historical sessions exist at a slot, or when the user selects Rolling 20-bar explicitly. The active mode is shown inline in the dashboard's Volume row (`TOD`, `20-bar`, or `20-bar*` for an in-flight TOD→fallback), prefixed `proxy·` when the volume series is coming from an index proxy. The volume series feeding all of this is `vol_eff` (proxy or chart) — see below.

**Index Data Proxy:** a cash-index feed (SPX, IXIC/NDX, S&P/TSX, NDQ, forex‑style index CFDs) usually reports `volume` as `na`/0. That silently guts scoring: `ta.vwap` returns `na` so **Component 2** scores 0, `rel_vol` pins to its `1.0` fallback so **Component 3** is a fixed 5/25, **Component 5B**'s `rel_vol > 1.5` tier is unreachable (caps at 3), and **Gate 4** can't evaluate. On the MARKET profile that pushes the realistic score ceiling below `min_score_auto` (55) — the indicator barely fires on a cash index. Fix: when `syminfo.type == "index"` **and** the chart doesn't carry real volume (`chart_has_volume`, a `var` latch that trips only once ≥50% of the last 100 bars carried volume — a single sporadic tick-count bar on an aggregated index feed must not flip it, which is why it's a sustained-majority test and not a first-nonzero-bar latch; monotonic, so no warm-up flicker), borrow VWAP + relative-volume from a liquid tradable proxy that tracks the index nearly tick-for-tick in RTH.
- **Proxy selection** (`proxy_ticker`): auto by `syminfo.ticker` substring, **no input** — `NDX`/`IXIC`/`NDQ`/`NAS100`/`US100`/`USTEC` → `NASDAQ:QQQ`; `TSX`/`TX60`/`SPTSX` → `TSX:XIC`; `SPX`/`SP500`/`US500`/`GSPC` → `AMEX:SPY`. Only these three families set `proxy_family_known` — an index the map doesn't recognize (DAX, FTSE, Nikkei, ...) does **not** use a proxy (it would otherwise be scored off `AMEX:SPY`, the ternary default); it falls to the session-TWAP substitute instead. To hand-pick a proxy — a different TSX ETF, a symbol you have data for — edit this chain in the `INDEX DATA PROXY` block; it's deliberately not a settings-panel control (light build).
- **One `request.security`** (in the `INDEX DATA PROXY` block, right after auto-tune resolution) pulls `[ta.vwap(close), close, volume, ta.sma(volume, len20)]` from the proxy on the chart timeframe with `lookahead_off` (same non-repaint contract as the daily ATR request). `proxy_ok` requires all four non-`na` and the vol-SMA/close positive; `use_proxy = proxy_eligible and proxy_ok`.
- **VWAP substitution:** `proxy_vwap_scaled = close * (proxy_vwap / proxy_close)` — the proxy's *fractional* VWAP deviation expressed at index price scale, so Component 2's `(close - vwap) / vwap` math needs no change. `vwap` is reassigned once, just before Component 2: chart-volume → real `ta.vwap`; volume-less index + proxy → `proxy_vwap_scaled`; volume-less index, no proxy → `session_twap`; volume-less **non**-index → left as the `na` `ta.vwap` (unchanged, Component 2 stays inactive). `session_twap` is a `var`-accumulated running mean of `hlc3` **anchored to the `tradingHours` RTH window** (reset when a local `time(timeframe.period, tradingHours)` goes non-`na`, *not* on `is_new_session`) — a 24h index CFD would otherwise average ~9h of overnight bars into the fair-value line before the cash open. It's computed with its own `time()` call because `in_session`/`session_just_opened` aren't defined until later in the file.
- **Volume substitution:** `vol_eff = use_proxy ? proxy_vol : volume` and `vol_ma_eff = use_proxy ? proxy_vol_ma : ta.sma(volume, 20)` feed `rel_vol_rolling`, `rel_vol_tod` and the Time-of-Day history push, so Components 3/5B and Gate 4 all run on proxy liquidity. `na` guards: `rel_vol_rolling`/`rel_vol_tod` require `not na(vol_eff)` (a proxy per-bar volume gap while its vol-SMA is still valid would otherwise make `rel_vol` `na` → Component 3 = 0 instead of the neutral `1.0`), and the Time-of-Day slot average skips `na` history entries (a `na` `vol_eff` pushed on a proxy-less-index bar would otherwise poison that bar-slot's average for every session it stays in `tod_vol_history`). The residual `: 1.0` fallback still catches "index with no working proxy" (and volume-less non-index).
- **Scope guard:** `proxy_eligible` is strictly `syminfo.type == "index" and not chart_has_volume`. Stocks/ETFs/futures (have volume) and forex (`type == "forex"`, not `"index"`) never trigger the proxy — a volume-less forex pair keeps its current dead-Component-2 behaviour rather than being scored off SPY.
- **Dashboard:** the **Profile** row appends `· <proxy_ticker> data` when `use_proxy`, or an orange `· ⚠️ volume-less → TWAP` when the symbol is proxy-eligible but no proxy is active (unrecognized family, or `proxy_ok` false). The Volume row's mode label gains the `proxy·` prefix.
- **Non-repainting:** `request.security(..., lookahead_off)` on the chart timeframe recomputes identically on historical bars; the realtime proxy bar updates intrabar exactly as chart volume already does. `session_twap` and the `chart_has_volume` sustained-majority latch are both confirmed-safe. No signal-timing guarantee changes.
- **Known limits:** delayed proxy data still works for signal generation but lags; a symbol whose ETF (`TSX:XIC`) the user's plan lacks fails `proxy_ok` and falls to `session_twap` (still far better than a dead component); an unrecognized index family (Dow, Russell, DAX, Nikkei, ...) gets `session_twap` for Component 2 and the `1.0` RVOL floor for Component 3 — to give it a real proxy, add its ticker pattern to the `proxy_ticker` / `proxy_family_known` chain. Proxy thresholds inherit the 2-min calibration caveat like everything else.

## Pine Script v6 Gotchas

Common failure modes when editing this script:

- **`var` variables** persist across bars and only initialize on bar 0. Do not use `var` for values that must recompute each bar (e.g., profile thresholds). The profile threshold variables (`vwap_h_limit`, `ema_max`, etc.) deliberately omit `var` so they reassign every bar.
- **`request.security` series vs simple:** The daily ATR (`atr_14`) uses `lookahead = barmerge.lookahead_off`. Omitting this causes future-bar lookahead (repainting). Always pass the expression directly — do not pre-compute into a `var` before passing to `request.security`.
- **`na` propagates through arithmetic:** `math.max(na, 0)` returns `na`, not 0. Always guard with `not na(x)` or `nz(x, 0)` before arithmetic involving potentially uninitialized series. This script uses explicit `not na(...)` checks before VWAP and session range calculations.
- **`barstate.isconfirmed` on historical bars:** All historical bars are "confirmed" during replay. `barstate.islast` is true only on the most recent bar. The dashboard uses `barstate.islast`; signals use `barstate.isconfirmed`.
- **`ta.crossover`/`ta.crossunder` are single-bar events:** They return `true` for exactly one bar. No multi-bar guard is needed; however, both require at least 2 bars of history.
- **`array.get` throws on out-of-bounds:** Always check `array.size(arr) > 0` before accessing index 0. The success rate arrays are guarded by `totalTrades_buy > 0` before the win-count loop.
- **`time()` session strings use ET for US equities** but the exchange timezone for other instruments. `tradingHours` (default `"0930-1600:23456"`, user-configurable via `input.session`, applied to every profile) is evaluated against whatever timezone that means for the loaded symbol — correct by default for US stocks; a crypto or 24h futures symbol may need the window widened (see "Trading Hours" note above) since it no longer gets an automatic profile-level exemption.
- **`str.split` includes empty strings** if the delimiter appears at the start/end of the string. `gate_message` is built with a trailing space, so `str.split(gate_message, " ")` always yields a trailing empty token. The word-wrap loop never turns this into a visible row, though: an empty word either merges into the current line as a harmless trailing space (line stays under the 30-char cap) or, if a line break is forced first, becomes `current_line := ""`, which the final `if current_line != "": array.push(...)` guard then excludes. No blank row is ever pushed to `gate_lines`.
- **`var table` cells persist across renders** — `table.cell` only overwrites the cells you write this bar. Any row written on a previous render and *not* rewritten keeps its old text forever. The dashboard therefore calls `table.clear(...)` before writing, because the gate-detail loop writes a variable number of rows.
- **`nz()` has no bool overload** — `nz(someBool[1], someBool)` fails with `CE10123` (`nz` expects a numeric `source`). To default a `bool`'s previous value, keep a second `var bool` and assign it from the first *before* the current bar's update, rather than reading `[1]`. `sma_prev_bull` in the SMA anchor does this; note that `[1]` on a `var bool` is `na` on bar 0, so an unguarded history read makes derived booleans `na` rather than `false`.
- **Arrays cannot nest** — `array<array<float>>` does not compile. To build a 2D/ragged structure (`TodSession` for Time-of-Day RVOL, `ModResults` for per-module win-rate), wrap the inner array in a user-defined `type` and use `array<TodSession>` / `array<ModResults>` instead. A function *can* mutate such an inner array in place (`array.push`/`array.shift` on `array.get(store, i).field`) — reference types reached through a parameter are fair game; only reassigning a value-type global is forbidden.
- **Functions cannot reassign a value-type global variable** (`float`/`int`/`bool`/`string`), even one declared with `var` — attempting `pnl_entry_price := close` inside a `set_pnl_entry(dir) =>` function fails to compile with `CE10088 Cannot modify global variable`. Only reference types (`array`/`matrix`/`map`/UDT) can be mutated from inside a function, and only via a parameter (e.g. `record_module(array<ModResults> store, ...)` calling `array.push` / `array.shift` on `array.get(store, id).buys`). This is why the P&L entry/re-arm logic (`pnl_entry_price`, `pnl_direction`, `pnl_exit_fired`) stays inlined at each of the 8 signal branches instead of being factored into a helper function — wrapping that state in a UDT to allow a helper would touch every read site across the file.
- **A user-defined function's return value is always `series`-qualified**, regardless of how "simple" its internal computation is — Pine can't verify a function stays `simple` across every possible call site, so it conservatively widens every function's result. This breaks `ta.ema`/`ta.sma`/`ta.atr`/`ta.rsi`/`ta.dmi`/`ta.bb`, whose `length` argument requires `simple int`: wrapping `math.round(base_len * tf_scale)` in a `scale_len(base_len) =>` helper (see [Timeframe Length Scaling](#timeframe-length-scaling)) fails with `CE10123 ... "series int" ... "simple int" is expected`, even though `tf_scale` itself is `simple` (built from `timeframe.in_seconds()`, a `simple int`). The fix is to inline the arithmetic as a plain expression assigned to a `simple int` variable and reuse that variable by reference — a variable reference doesn't widen the qualifier the way a function call does. This is a stricter version of the "can't reassign a global" rule above: it's not just mutation that's restricted through a function boundary, it's the qualifier of the return value itself.
- **`time_close(timeframe, session)` does not reliably detect "the bar whose close crosses the session boundary"** the way it might seem to from `time(timeframe, session)`'s documented behavior (which returns `na` once the bar's *open* falls outside session). An attempt to detect the last in-session bar via `is_last_session_bar = in_session and na(time_close(timeframe.period, tradingHours))` (reasoning: a bar's own close timestamp is already known the moment it opens, so testing it against the session shouldn't need look-ahead) compiled fine but never actually fired in testing — see "Trading Hours forced day-end resolution" in [Key Design Decisions](#key-design-decisions). The reliable alternative for "did the session just end" is the same pattern already used for "did the session just open": compare `in_session` against `in_session[1]` (`session_just_closed = not in_session and prev_in_session`) rather than trying to catch the exact boundary bar directly. This fires one bar late (on the first off-hours bar); compensate by reading `close[1]`/`bar_index[1]` for the price and label position that actually belong to the session's real last bar, rather than trying to eliminate the one-bar lag.
