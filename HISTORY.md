# HISTORY.md

Release-to-release changelog for `SLT.pine` — what changed, why, which experiments were tried and reverted, and the relevant commit hashes.

This file is **not** loaded into the model context by default (that's the point of splitting it out of `CLAUDE.md`). `CLAUDE.md` describes only the *current* behaviour of each subsystem; this file is the running history behind it. Append new entries at the end, newest last.

---

## Lineage

The script file is `SLT.pine`. It was forked from **SuperLazyTrade V3** with the SuperTrend signal anchor removed entirely (input option, SuperTrend Engine settings group, adaptive ATR/factor block, `ta.supertrend` call, `st_*` anchor, its plots/fills/circles, dashboard branch). Anchor selection is binary — SMA (default) or EMA Cross. The on-chart `indicator()` title is `SLT V1` (from `VERSION = "V1"`).

---

## Changelog

**Light-build simplification (current):** the input surface is Signal Anchor, Score Stars, P&L Exit, Trading Hours, and two Dashboard & Visuals toggles (`showDash` / `extDash`). Former inputs are auto-tuned from the asset profile + anchor (`ema_slow_auto` / `sma_buf_auto` / `min_score_auto` → `emaSlowPeriod` / `smaBufferATR` / `minScore*`, plus `maxBarsFromFlip` from the anchor) or pinned as constants (`sigTime="Score"`, `gateOn=true`, `rvolMode="Time-of-Day"`, SMA MANUAL mode dropped, success-rate + `showSignalPnL` + `showLabels` + `showCircles`; the `showBg` trend-background toggle was removed outright since the light build has no `bgcolor()`). The **VWAP Fade** module is deleted; the **ORB** module is retained but inert (`orbEnabled=false` constant). (A Component 1 anchor-decoupling — commit `c0d85a1` — was tried for cross-anchor score comparability and reverted; it broke the term's directionality.) The on-chart `indicator()` title is `SLT V1` (from `VERSION = "V1"`).

**Trading Hours — now a user input applied to every asset type (current):** previously the RTH session filter was profile-derived (`rth_auto`: `true` for MARKET/FUND/STOCK, `false` for FUTURES/CRYPTO so a 24h contract wouldn't get RTH-blacked-out). This caused the reported bug: futures signals fired with no hours restriction at all, any time of day. Replaced `rth_auto`/`useSessionFilter` entirely with a single always-enforced user input, `tradingHours` (`grp_hours`, `input.session`, default `"0930-1600:23456"`), read by `in_session`/`session_just_opened` via `time(timeframe.period, tradingHours)` for every profile uniformly — no per-profile exception and no on/off toggle. To run a symbol with no hours restriction, widen the session (e.g. `"0000-2359:1234567"`) in the input itself. See "Trading Hours" in [Key Design Decisions](CLAUDE.md#key-design-decisions).

**Gate change — velocity override extended to Gate 2:** `is_high_velocity` (`ADX > 35` rising 3 bars) now waives the Stretch penalty as well as the ATR-Fuel penalty. A strong, still-accelerating trend that has run past `ext_scale` ATR keeps its `final_score` intact instead of being docked −10/−20 and pushed below the star filter. The raw stretch tier is still shown as advisory (`gate2_raw`, gate message reads `🔥 VELOCITY` in place of `-N`); only the score subtraction and `active_gate_count` are suppressed. Implemented as `gate2_stretched = gate2_raw and not is_high_velocity`, mirroring the pre-existing `gate3_fuel` pattern.

**Dashboard — Strategy row removed:** the `active_strategy · <regime>` row is deleted. In the light build `active_strategy` is always `Trend Pullback`, and `regime` (the `SQUEEZE`/`BREAKOUT`/`EXHAUSTED`/`TREND`/`RANGE` string) had no consumer left after VWAP Fade — so `regime` and `sqz_bias` are deleted from `SLT.pine` too. Signal generation is now three sub-stages (strategy modules → router → dispatch).

**Win-rate change — unresolved reversals excluded (current):** previously a signal reversed before ever hitting PROFIT or LOSS was scored as a **loss** (the array push was `won ? true : false` with no third state). Now such an entry is excluded from `buy_results`/`sell_results`/`mod_results` entirely — win rate is a clean wins/(wins+losses) ratio over resolved entries only. Added `buy_lost_this_entry`/`sell_lost_this_entry` (parallel to the existing `*_won_this_entry` flags, set from `stop_reached`) and `buy_signals_fired`/`sell_signals_fired` (`var int`, uncapped, incremented at every signal open) to show total signals fired alongside the resolved win/loss count — dashboard format changed from `<rate>% [<w>/<t>]` to `<rate>% [<w>/<t>] (<N> fired)`. See [Win-rate tracking](CLAUDE.md#key-design-decisions).

**Day-end forced P&L resolution (current):** the Trading Hours input (previous entry) fixed signal *entries*, but PROFIT/LOSS *exits* still had no trading-hours gate at all — `current_pnl` kept evaluating on every confirmed bar regardless of session, so an off-hours price swing could still fire a PROFIT/LOSS label outside trading hours. Fixed by adding a day-end forced resolution, detected via `session_just_closed = not in_session and prev_in_session` (the first off-hours bar — same proven primitives as `session_just_opened`, just inverted). A first attempt tried detecting the last in-session bar directly via `time_close(timeframe.period, tradingHours)` returning `na`; that never actually fired in testing (`time_close` didn't behave like `time` does for this), so it was replaced with the one-bar-late `session_just_closed` approach, which reuses proven logic. `day_end_pnl` is computed from `close[1]` (the real last-in-session price) and, if the position is still open and unresolved, `day_end_win_hit`/`day_end_loss_hit` force it to resolve by that sign, OR'd directly into the existing `target_reached`/`stop_reached` booleans. Every downstream consumer — win-rate scoring, `pnl_exit_fired`, the PROFIT/LOSS alertcondition — picks this up with no new plumbing. The exit label shows the real P&L instead of the fixed target text for this path (`PROFIT +0.7%` / `LOSS -0.3%` rather than `PROFIT +1.0%` / `LOSS -1.0%`) and is anchored back to `bar_index - 1`/`close[1]` so it appears at the correct bar even though the code runs one bar late. Net effect: every entry now resolves (won or lost) within the trading day it opened — it can only go "unresolved"/excluded (see the win-rate change above) via a same-day reversal before the session closes, never by drifting unresolved across sessions. See "Trading Hours forced day-end resolution" in [Key Design Decisions](CLAUDE.md#key-design-decisions).

**Timeframe length scaling (current):** every bar-count lookback (EMA9/20/50, the profile SMA length, ATR/RSI/ADX(14), the squeeze BB/KC(20) lengths, the 20-bar RVOL fallback, `maxBarsFromFlip`) is now rescaled by `tf_scale = 120 / timeframe.in_seconds()` so each keeps covering the same wall-clock window on any chart interval, not just the tested 2-min chart. At `tf_scale = 1.0` (i.e. on a 2-min chart) nothing changes — see [Timeframe Length Scaling](CLAUDE.md#timeframe-length-scaling). Profile threshold/percentage values (`vwap_h_limit`, `adx_min`, `ext_scale`, `fuel_max`, RVOL tiers) are explicitly *not* rescaled — they have no comparable scaling law and stay validated only at 2-min. Implemented as inline `simple int` expressions (`len9`/`len14`/`len20`/`len50`/`len10`), not a shared helper function — a `scale_len()` function was tried first and failed to compile (`CE10123`), since Pine widens any user-defined function's result to `series`, which `ta.ema`/`ta.sma`/`ta.atr`/`ta.rsi`/`ta.dmi`/`ta.bb` reject for their `length` argument.

**Scoring change — MACD dropped (commit `9284b73`):** Component 5's MACD sub-component (was 5A, 8 pts, "MACD line same sign as trend direction") is removed. MACD-line sign ≈ `EMA12 > EMA26`, a near-duplicate of Component 1's EMA cascade, so it carried almost no independent signal. Its 8 points were redistributed proportionally (old 7:5 split) across the two survivors — RSI 7→12 (now 5A), Squeeze Release 5→8 (now 5B). Component 5 max stays 20 and the 105 pre-cap total is unchanged. The `ta.macd(close,12,26,9)` call, `macd_aligned` / `macd_pts`, and the `MACD: ✓/✗` field in `r_status` are all deleted; `r_status` tier thresholds re-cut to `16 / 12 / 8 / 3` for the new point distribution (cosmetic — the label never feeds `raw_score`).

**Code-review fix pass on day-end forced resolution (commits `0ba81e7`, `56dee3f`, `0cce0e7`):** a `/code-review` of the previous session's day-end forced-resolution commit (`343fd9a`) surfaced 8 findings; all were fixed. **Two high-severity correctness bugs:** (1) an entry opened on the exact bar a day-end trigger resolves has `close[1]` trivially equal to its own entry price, so it was being force-scored a meaningless exact-0% "win" with zero market exposure — fixed by adding `pnl_entry_bar` (the entry's opening `bar_index`) and requiring `pnl_entry_bar < bar_index - 1` in `day_end_close`, leaving such an entry unresolved instead. (2) day-end forced resolution silently never engaged for a `tradingHours` window widened to cover every bar (e.g. `"0000-2359:1234567"`, the very workaround this file itself suggests for 24h symbols) — `session_just_closed` can never fire there since `in_session` never goes false. Fixed by adding `day_end_fallback` (keyed off the pre-existing calendar-day-rollover detector `is_new_session`) OR'd into a new `day_end_trigger`; this also required re-keying the exit-label `is_day_end` flag off `day_end_win_hit`/`day_end_loss_hit` directly rather than `not in_session`, since the fallback can fire while `in_session` stays true throughout. **Three more fixes:** a pre-existing win-rate double-count (`buy_entry_open`/`buy_won_this_entry` weren't cleared at the opposite-signal close that consumed them, only at the next `session_just_opened`, so a stale resolved entry could get pushed into `buy_results` twice); a dashboard live-P&L staleness issue (`day_end_frozen_pnl` now freezes the displayed P&L at the day-end value instead of letting it keep drifting with the post-resolution close — normal in-session resolutions are unaffected); and two cleanup items (`day_end_pnl`'s division gated behind `day_end_trigger` instead of running every confirmed bar; the duplicated day-end label anchor/style logic between the PROFIT and LOSS blocks factored into `day_end_label_anchor()`/`exit_label_style()`). **One limitation documented rather than fixed:** `tradingHours` is designed for a single continuous range — a comma-separated multi-range session string (e.g. a lunch-break split) makes `session_just_opened`/`session_just_closed` fire at every internal gap, which would force day-end resolution mid-day; not safely fixable without parsing `tradingHours` itself, so it's called out in the input's tooltip and a code comment instead. See "P&L exits fire on target/stop hit", "Trading Hours forced day-end resolution", and "Win-rate tracking" in [Key Design Decisions](CLAUDE.md#key-design-decisions), and checklist items 18–19. User confirmed all three commits compile clean.

**Fired-count windowed to trailing 20 trading sessions (current):** `buy_signals_fired`/`sell_signals_fired` were plain `var int` lifetime counters — an all-time, never-reset, uncapped total for the whole loaded chart. On any chart with more history than `maxSignalsToTrack` (50) signals, the growing gap between `(N fired)` and the capped `[w/t]` resolved total became mostly an artifact of chart length rather than a meaningful "how many entries never resolved" signal. Replaced with a rolling window over the trailing `FIRED_LOOKBACK_SESSIONS` (20, new `const int`) **trading sessions** — chosen over raw calendar-day subtraction so weekend/holiday gaps don't shrink the window below ~20 real trading days, matching the existing `rvolLookbackDays` convention. Implementation: a new `session_seq` (`var int`) increments once per `is_new_session` (the same calendar-day-rollover detector the ATR Fuel gauge and Time-of-Day RVOL already rely on); `buy_fire_sessions`/`sell_fire_sessions` (`var array<int>`) push `session_seq` at every signal open (same hook the old counters used); every bar, a `while` loop trims entries off the front of each array once they fall `FIRED_LOOKBACK_SESSIONS` sessions behind — a plain front-trim is correct (and cheap — no full-array scan) because pushes always arrive in non-decreasing `session_seq` order. `buy_signals_fired`/`sell_signals_fired` are now `array.size(...)` of the trimmed arrays, recomputed every bar. **Known consequence, documented rather than "fixed":** because `[w/t]` is windowed by signal *count* (`maxSignalsToTrack`) and `fired` is now windowed by *session*, the two windows are independent — a low-frequency symbol could hold 50 resolved entries spanning more than 20 sessions, at which point `fired` can under-count relative to `[w/t]`. The previous lifetime-counter design trivially guaranteed `fired ≥ [w/t]`'s resolved total; that invariant no longer holds. See "Fired-count rolling window" in [Key Design Decisions](CLAUDE.md#key-design-decisions) and checklist item 24.

**Trade Signal verdict row added (current):** a new `Trade Signal` dashboard row, placed right after Setup Score (before Gates) — deliberately not grouped with the BUY/SELL Win Rate rows it reads from — turns the resolved win-rate stats for whichever direction fired *last* into a plain TRADE/CAUTION/SKIP/WAIT call, so the user doesn't have to mentally adjust the raw win rate for sample size and signal-reliability. Built from three new pinned constants (`VERDICT_MIN_SAMPLE=10`, `VERDICT_MIN_RESOLUTION=0.40`, `WILSON_Z=1.96`) and two new read-only helpers, `wilson_lower_bound()` (Wilson score lower-bound win rate, shrinks toward 50% for small samples) and `trade_verdict()` (applies the minimum-sample gate, then the resolution-rate floor, then the Wilson-adjusted 60/50 tier cutoffs already used for the win-rate row colors, and appends the implied expectancy `pnlTarget × (2×wlb−1)`). Tracks one direction at a time (`last_signal_type`) rather than a combined or dual-row design — a deliberate choice, since a live BUY and a live SELL are never both "the current call" simultaneously under strict alternation. Originally placed next to the win-rate rows and considered for the dashboard title row; both were rejected — the title row can't color-code the verdict (one Pine table cell = one text color for the whole string) and the user preferred it stand apart from Success Rate Tracking as its own line. `DASHBOARD_MAX_ROWS` stays at 36 (one more fixed row, still well under budget; Success Rate Tracking itself is unchanged at 3 rows). See "Trade Signal verdict" in [Key Design Decisions](CLAUDE.md#key-design-decisions) and checklist item 25.

**ATR Fuel row moved to Extended Metrics (current):** the `ATR Fuel` row used to be an always-on core dashboard row (white label, no color-coding), right before Setup Score. User feedback: it wasn't actionable for a trading decision, since its effect (Gate 3's −25 penalty) is already reflected in the Gates row, Setup Score, and now the Trade Signal verdict. Rather than delete it outright, it was moved into Extended Metrics (`extDash`), right after the existing `Volatility` row (ATR(14)/session range) it's thematically closest to — kept rather than removed because it's still the only place showing `🔥 VELOCITY OVERRIDE` (Gate 3's penalty waived by `is_high_velocity`), a state the Gates row's plain "NO ACTIVE" can't distinguish from a day with no fuel exhaustion at all. No logic changed — `fuel_used`/`fuel_max`/`is_high_velocity`/Gate 3 itself are untouched; only the dashboard row moved and is now gated on `extDash`.

**Dashboard title truly centered (current):** the header row (`SLT V1 | PnL ...`) was padded with trailing spaces out to 40 characters (`DASH_WIDTH`) before `text_halign = text.align_center` was applied — centering text-plus-padding visually left-justifies the real text instead. Removed the padding (and the now-unused `DASH_WIDTH` constant); the header cell's width already comes from the widest row below it via `table.merge_cells`, so no padding was needed for sizing. Purely cosmetic — no data/logic change.

**Doc/code-consistency fix pass (commit `d3e4a3f`):** a CLAUDE.md-vs-code diff found four items, all resolved. (1) Component 5A RSI: the bear 12-pt "high-conviction" tier fired at RSI < 45 (near-neutral) while the bull side needs RSI > 60 — tightened to RSI < 40 so the two sides mirror symmetrically about 50, matching the doc's "bear is the mirror". (2) CLAUDE.md's Setup-quality section still called `minScoreBuy`/`minScoreSell` "user inputs, range 0–70" — corrected to auto-resolved `min_score_auto` (45–55). (3) `extDash` tooltip claimed it adds the win-rate rows (they render under `enableSuccessRate` regardless) — reworded. (4) `showBg` removed outright: the parent's trend-background `bgcolor()` was dropped in the light build, so the pinned constant gated nothing; the SMA buffer band's `fill()` now shades unconditionally in SMA mode.

**Index Data Proxy for volume-less cash indices (current):** cash indices (SPX, IXIC/NDX, S&P/TSX, ...) report no volume, which silently disabled Component 2 (VWAP → `na` → 0 pts), pinned Component 3 to its 5-pt floor, capped Component 5B at 3, and made Gate 4 inert — dropping the realistic MARKET-profile score ceiling below `min_score_auto` (55) so the indicator barely fired on an index. Added an `INDEX DATA PROXY` block (after auto-tune resolution): when `syminfo.type == "index"`, the chart has never shown positive volume (`chart_has_volume`, a `var` latch), and the symbol family is recognized (`proxy_family_known` — S&P 500 / Nasdaq / S&P-TSX ticker patterns), one `request.security(proxy, timeframe.period, [ta.vwap(close), close, volume, ta.sma(volume, len20)], lookahead_off)` pulls VWAP + relative-volume from a liquid tracking ETF. `proxy_ticker` is a hardcoded symbol-family map (QQQ / XIC / SPY) — **no user input** (removed after first cut for the light-build minimal-panel principle; to hand-pick a proxy, edit the chain). `vwap` is reassigned once before Component 2 — real `ta.vwap` for volume-bearing symbols, `proxy_vwap_scaled` (proxy VWAP rescaled to index price units) when `use_proxy`, a session TWAP (`hlc3` running mean) for an index with no working/recognized proxy, and unchanged (`na`) for volume-less non-index symbols like forex. `vol_eff`/`vol_ma_eff` route proxy volume into `rel_vol_rolling`/`rel_vol_tod` and the Time-of-Day history. Dashboard: the Profile row shows `· <proxy> data` (or an orange `· ⚠️ volume-less → TWAP`), the Volume row's mode label gains a `proxy·` prefix. Non-repainting (`lookahead_off`, same contract as the daily ATR request); no signal-timing guarantee changes. See "Index Data Proxy" in [Key Design Decisions](CLAUDE.md#key-design-decisions) and checklist item 26.

**Index-proxy code-review fix pass:** a `/code-review` of the proxy feature raised four issues, all fixed. (1) `chart_has_volume` was a first-nonzero-bar `var` latch — a single sporadic tick-count bar on an aggregated index feed would permanently disable the proxy for the whole chart; changed to a monotonic latch that trips only on a **sustained ≥50% of the last 100 bars** carrying volume. (2) `session_twap` reset on `is_new_session` (calendar day), so a 24h index CFD averaged ~9h of overnight bars into the fair-value line before the cash open; re-anchored to the `tradingHours` RTH window via a local `time()` call. (3) the Time-of-Day slot average summed history entries with no `na` guard — a `na` `vol_eff` (proxy-less-index bar, or rare proxy gap) pushed into `tod_vol_history` poisoned that bar-slot's average for ~10 sessions; now `na` slots are skipped. (4) `rel_vol_rolling`/`rel_vol_tod` gained a `not na(vol_eff)` guard so a proxy per-bar volume gap (while the proxy vol-SMA is still valid) yields the neutral `1.0` rather than `na` → Component 3 = 0.

**Win-rate: one session window, W/L/U buckets (current — supersedes the two entries above about unresolved-exclusion and the fired-count window):** the win rate `[w/t]` was capped at `maxSignalsToTrack` (50) resolved trades by *signal count*, while `(N fired)` was windowed to `FIRED_LOOKBACK_SESSIONS` (20) *trading sessions* — two independent windows, so on a long/uneven history `fired` and the resolved total didn't compose (`fired − resolved` could go negative; the verdict's `resolution_rate = total/fired` could exceed 1.0). Replaced the `buy_results`/`sell_results` bool arrays **and** the `buy_fire_sessions` counters with **six `var array<int>`** — `buy_win_s`/`buy_loss_s`/`buy_unr_s` and the SELL trio — each holding the `session_seq` at **trade close**, front-trimmed every bar to the trailing `WINRATE_LOOKBACK_SESSIONS` (**15**, replacing `FIRED_LOOKBACK_SESSIONS`). Every closed trade lands in exactly one bucket: **W** (PROFIT fired), **L** (LOSS fired), or **U** (reversed same-day, never hit either — now its own bucket, no longer silently excluded). `buy_w`/`buy_l`/`buy_u` = the trimmed sizes; `success_rate_buy` = `W/(W+L)`, `totalTrades_buy` = `W+L`, verdict `fired` = `W+L+U` — one window, everything composes. Dashboard row changed from `<rate>% [<w>/<t>] (<N> fired)` to `<rate>%  ·  <W>W <L>L <U>↺` (rate grey when `W+L=0`). `add_result` deleted, `winrate_stats()` added; `calc_win_rate` kept for the (still bool-array, still signal-count-capped, still suppressed) per-module rows. `maxSignalsToTrack` now caps only `mod_results`. Inlined `while` trims (no UDF) to stay on the proven pattern. See "Win-rate tracking" in [Key Design Decisions](CLAUDE.md#key-design-decisions) and checklist items 13 / 24.

**Win-rate trim cleanup:** a `/code-review` of the W/L/U rework noted the six copy-pasted `while` front-trim blocks and that their inline comment's rationale ("a `while` inside a UDF is avoided") was unfounded — a UDF mutating an array passed by reference is legal and `record_module()` already does it. Folded the six blocks into one `trim_window(array<int> a, int cutoff)` helper (a `while` + `array.shift`), called once per bucket. No behaviour change; a future edit to the trim rule is now one place instead of six.
